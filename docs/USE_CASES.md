# BimorShop – Анализ вариантов использования

## Акторы

### **Гость (Неавторизованный пользователь)**
Пользователь, который не выполнил вход в систему. Может просматривать каталог товаров, но не может создавать заказы или добавлять в избранное.

### **Покупатель**
Авторизованный пользователь, который может просматривать товары, создавать заказы, добавлять товары в избранное и управлять своим профилем.

### **Продавец**
Авторизованный пользователь, который размещает товары в магазине. Может управлять своим каталогом товаров и просматривать свои заказы.

### **Система (Backend API)**
REST API приложение на Spring Boot, обрабатывающее запросы от фронтенда и взаимодействующее с базой данных.

## Сценарии вариантов использования

### **UC1: Регистрация нового пользователя**

**Актор:** Гость  
**Предусловие:** Пользователь не авторизован в системе.

**Основной поток событий:**
1. Пользователь переходит на страницу регистрации
2. Система отображает форму регистрации с полями:
   - Nickname (уникальный)
   - Имя
   - Фамилия
   - Email (уникальный)
   - Телефон (уникальный)
   - Пароль (минимум 6 символов)
3. Пользователь заполняет все обязательные поля
4. Пользователь нажимает кнопку "Зарегистрироваться"
5. Система проверяет уникальность nickname, email и телефона
6. Система валидирует формат email и минимальную длину пароля
7. Система создает новый аккаунт в базе данных
8. Система автоматически выполняет вход пользователя
9. Пользователь перенаправляется на главную страницу

**Альтернативные потоки:**
- **A1:** Email уже существует → Система возвращает ошибку "Email уже зарегистрирован"
- **A2:** Телефон уже существует → Система возвращает ошибку "Телефон уже зарегистрирован"
- **A3:** Nickname уже существует → Система возвращает ошибку "Nickname уже занят"
- **A4:** Невалидный email → Система возвращает ошибку "Некорректный формат email"
- **A5:** Слишком короткий пароль → Система возвращает ошибку "Пароль должен содержать минимум 6 символов"
- **A6:** Пропущено обязательное поле → Система возвращает ошибку "Заполните все обязательные поля"

**Постусловие:** Новый аккаунт создан, пользователь авторизован и может использовать все функции системы.

---

### **UC2: Вход в систему**

**Актор:** Гость  
**Предусловие:** Пользователь имеет зарегистрированный аккаунт.

**Основной поток событий:**
1. Пользователь переходит на страницу входа
2. Система отображает форму входа с полями:
   - Email
   - Пароль
3. Пользователь вводит email и пароль
4. Пользователь нажимает кнопку "Войти"
5. Система ищет пользователя по email в базе данных
6. Система проверяет соответствие пароля
7. Система создает сессию пользователя
8. Система перенаправляет пользователя на главную страницу
9. Система отображает приветственное сообщение

**Альтернативные потоки:**
- **A1:** Email не найден → Система возвращает ошибку "Пользователь с таким email не найден"
- **A2:** Неверный пароль → Система возвращает ошибку "Неверный пароль"
- **A3:** Пропущены обязательные поля → Система возвращает ошибку "Введите email и пароль"

**Постусловие:** Пользователь авторизован, сессия создана, доступны все функции системы.

---

### **UC3: Просмотр каталога товаров**

**Актор:** Любой пользователь (Гость, Покупатель, Продавец)  
**Предусловие:** Система содержит товары в базе данных.

**Основной поток событий:**
1. Пользователь переходит на главную страницу
2. Система загружает список товаров из базы данных
3. Система отображает товары в виде сетки карточек, каждая карточка содержит:
   - Изображение товара (если есть)
   - Название товара
   - Цену
   - Категорию
   - Кнопки действий (Подробнее, В избранное, В корзину)
4. Пользователь может пролистывать товары
5. Пользователь может фильтровать товары по категории
6. Пользователь может искать товары по названию

**Альтернативные потоки:**
- **A1:** Нет товаров в базе → Система отображает сообщение "Товары не найдены"
- **A2:** Пользователь применяет фильтр по категории → Система загружает только товары выбранной категории
- **A3:** Пользователь выполняет поиск → Система фильтрует товары на клиенте по введенному запросу
- **A4:** Пользователь не авторизован → Кнопки "В избранное" и "В корзину" неактивны

**Постусловие:** Пользователь просмотрел каталог товаров, может перейти к детальному просмотру или совершить действие с товаром.

---

### **UC4: Добавление товара в избранное**

**Актор:** Покупатель  
**Предусловие:** Пользователь авторизован и просматривает каталог товаров.

**Основной поток событий:**
1. Пользователь нажимает кнопку "❤" на карточке товара
2. Фронтенд отправляет POST запрос на `/api/orders/favorite` с параметрами:
   - `accountId` - ID текущего пользователя
   - `productId` - ID товара
3. Backend создает специальный заказ с флагом `favorite = true`
4. Backend связывает заказ с пользователем и товаром
5. Backend возвращает успешный ответ
6. Фронтенд обновляет состояние кнопки (активная/неактивная)
7. Система показывает уведомление "Товар добавлен в избранное"

**Альтернативные потоки:**
- **A1:** Товар уже в избранном → Система выполняет DELETE запрос и удаляет из избранного
- **A2:** Пользователь не авторизован → Система перенаправляет на страницу входа
- **A3:** Ошибка сервера → Система показывает уведомление "Не удалось добавить в избранное"

**Постусловие:** Товар добавлен в избранное пользователя, пользователь может просмотреть его в своем профиле.

---

### **UC5: Просмотр и управление избранным**

**Актор:** Покупатель  
**Предусловие:** Пользователь авторизован и имеет товары в избранном.

**Основной поток событий:**
1. Пользователь переходит в раздел "Профиль" → "Избранное"
2. Система отправляет GET запрос на `/api/orders/favorite/{accountId}`
3. Backend возвращает список товаров в избранном
4. Фронтенд отображает список товаров в компактном виде
5. Пользователь может:
   - Просмотреть детали товара (клик по карточке)
   - Удалить товар из избранного (кнопка "Удалить")
   - Перейти к оформлению заказа с этим товаром

**Альтернативные потоки:**
- **A1:** Нет товаров в избранном → Система отображает сообщение "Список пуст"
- **A2:** Пользователь удаляет товар → Система выполняет DELETE запрос и обновляет список

**Постусловие:** Пользователь просмотрел список избранных товаров, выполнил необходимые действия.

---

### **UC6: Создание заказа**

**Актор:** Покупатель  
**Предусловие:** Пользователь авторизован и выбрал товары для заказа.

**Основной поток событий:**
1. Пользователь выбирает товары для заказа
2. Пользователь нажимает кнопку "Оформить заказ"
3. Система отображает форму заказа с выбранными товарами
4. Пользователь подтверждает состав заказа
5. Фронтенд отправляет POST запрос на `/api/orders` с JSON:
   ```json
   {
     "account": {"id": userId},
     "productIds": [productId1, productId2, ...],
     "orderDate": "2024-01-15T10:30:00",
     "totalPrice": 150.0
   }
   ```
6. Backend проверяет существование пользователя и всех товаров
7. Backend создает заказ в базе данных
8. Backend устанавливает связи ManyToMany между заказом и товарами
9. Backend возвращает созданный заказ с ID
10. Система показывает уведомление "Заказ успешно создан"
11. Заказ отображается в истории заказов пользователя

**Альтернативные потоки:**
- **A1:** Один из товаров не найден → Система возвращает ошибку "Один или несколько товаров не найдены"
- **A2:** Пользователь не найден → Система возвращает ошибку "Пользователь не найден"
- **A3:** Пустой список товаров → Система возвращает ошибку "Необходимо указать ID продуктов"

**Постусловие:** Заказ создан, товары зарезервированы (если требуется), пользователь может отслеживать статус заказа.

---

### **UC7: Размещение товара в магазине**

**Актор:** Продавец  
**Предусловие:** Пользователь авторизован как продавец.

**Основной поток событий:**
1. Продавец переходит в раздел "Мои товары"
2. Продавец нажимает кнопку "Добавить товар"
3. Система отображает форму создания товара с полями:
   - Название товара (обязательно)
   - Цена (положительное число, обязательно)
   - Категория (обязательно)
   - Ссылка на изображение (опционально)
   - Описание (опционально)
4. Продавец заполняет форму
5. Продавец нажимает кнопку "Сохранить"
6. Фронтенд отправляет POST запрос на `/api/products` с JSON:
   ```json
   {
     "name": "Название товара",
     "price": 1000,
     "category": "Электроника",
     "imageUrl": "https://example.com/image.jpg",
     "account": {"id": sellerId}
   }
   ```
7. Backend создает товар в базе данных
8. Backend связывает товар с аккаунтом продавца
9. Система показывает уведомление "Товар успешно добавлен"
10. Товар появляется в каталоге магазина

**Альтернативные потоки:**
- **A1:** Пропущено обязательное поле → Система возвращает ошибку валидации
- **A2:** Цена не положительная → Система возвращает ошибку "Цена должна быть положительным числом"
- **A3:** Пакетное добавление → Продавец использует `/api/products/create-several-products` для добавления нескольких товаров

**Постусловие:** Товар добавлен в каталог магазина, доступен для покупки.

### **UC8: Каскадное удаление аккаунта**

**Актор:** Пользователь  
**Предусловие:** Пользователь существует в системе и имеет связанные данные.

**Основной поток событий:**
1. Администратор или пользователь инициирует удаление аккаунта
2. Система запрашивает подтверждение действия
3. После подтверждения фронтенд отправляет DELETE запрос на `/api/accounts/{id}`
4. Backend находит аккаунт по ID
5. Backend удаляет все заказы пользователя (каскадная операция благодаря `orphanRemoval = true`)
6. Backend удаляет аккаунт из базы данных
7. Backend возвращает HTTP статус 204 (No Content)
8. Если удалял сам пользователь - система выполняет выход
9. Система показывает уведомление "Аккаунт успешно удален"

**Альтернативные потоки:**
- **A1:** Аккаунт не найден → Система возвращает ошибку 404 "Аккаунт не найден"
- **A2:** У пользователя есть активные заказы → Возможно предупреждение или запрет удаления (в текущей реализации заказы удаляются каскадно)
- **A3:** Администратор удаляет аккаунт → Система может отправлять уведомление пользователю

**Постусловие:** Аккаунт и все связанные данные удалены из системы.

---

### **UC10: Управление профилем пользователя**

**Актор:** Любой авторизованный пользователь  
**Предусловие:** Пользователь авторизован.

**Основной поток событий:**
1. Пользователь переходит в раздел "Профиль"
2. Система отображает текущие данные пользователя:
   - Имя, фамилия
   - Nickname
   - Email
   - Телефон
   - Статистика (количество заказов, избранных товаров)
3. Пользователь нажимает кнопку "Редактировать"
4. Система отображает форму редактирования
5. Пользователь изменяет данные (кроме email и пароля - требуют отдельного процесса)
6. Пользователь нажимает кнопку "Сохранить"
7. Фронтенд отправляет PUT запрос на `/api/accounts/{id}` с обновленными данными
8. Backend обновляет данные пользователя в базе данных
9. Система показывает уведомление "Данные успешно обновлены"
10. Профиль обновляется с новыми данными

**Альтернативные потоки:**
- **A1:** Пользователь пытается изменить email → Система перенаправляет на отдельный процесс с подтверждением
- **A2:** Пользователь хочет изменить пароль → Система перенаправляет на форму смены пароля
- **A3:** Конфликт уникальности (nickname уже занят) → Система возвращает ошибку

**Постусловие:** Данные профиля пользователя обновлены в системе.

---

### **UC11: Поиск и фильтрация товаров**

**Актор:** Любой пользователь  
**Предусловие:** В системе есть товары.

**Основной поток событий:**
1. Пользователь вводит поисковый запрос в поле поиска
2. Фронтенд загружает все товары с бэкенда (в текущей реализации)
3. Фронтенд фильтрует товары на клиенте по:
   - Названию товара (содержит поисковый запрос)
   - Категории (содержит поисковый запрос)
4. Система отображает отфильтрованные товары
5. Пользователь может дополнительно применить фильтр по цене
6. Пользователь может сбросить фильтры

**Альтернативные потоки:**
- **A1:** Поиск не дал результатов → Система отображает "Товары не найдены"
- **A2:** Пользователь использует только фильтр по категории → Система отправляет запрос с параметром `?category=...`
- **A3:** Пользователь использует только фильтр по цене → Система отправляет запрос с параметром `?price=...`
- **A4:** Серверная фильтрация → В будущем будет реализована на бэкенде с пагинацией

**Постусловие:** Пользователь нашел нужные товары с помощью поиска и фильтрации.

---

### **UC12: Обработка ошибок и исключений**

**Актор:** Система (Backend)  
**Предусловие:** Возникла исключительная ситуация.

**Основной поток событий:**
1. В процессе выполнения операции возникает исключение
2. Spring Boot перехватывает исключение через `@RestControllerAdvice` или `@ExceptionHandler`
3. Система логирует ошибку (в текущей реализации частично)
4. Система определяет соответствующий HTTP статус:
   - `400 Bad Request` - ошибки валидации
   - `404 Not Found` - ресурс не найден
   - `500 Internal Server Error` - внутренняя ошибка сервера
5. Система возвращает JSON ответ с информацией об ошибке
6. Фронтенд отображает понятное сообщение об ошибке пользователю

**Типичные сценарии:**
- **S1:** Ресурс не найден → `ResourceNotFoundException` → HTTP 404
- **S2:** Ошибка валидации → `ValidationException` → HTTP 400
- **S3:** Внутренняя ошибка → `RuntimeException` → HTTP 500
- **S4:** Ошибка базы данных → SQL исключения → HTTP 500

**Альтернативные потоки:**
- **A1:** Фронтенд ошибка → JavaScript перехватывает ошибку и показывает уведомление
- **A2:** Сетевая ошибка → Фронтенд показывает сообщение "Нет соединения с сервером"

**Постусловие:** Ошибка обработана, пользователь получил информацию, система продолжает работу.
